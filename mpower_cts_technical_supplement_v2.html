Every concern a government technical team would raise — answered with exact technical specifications and honest build status. • ప్రతి సాంకేతిక సమస్యకు నిజాయితీగా సమాధానం.
❓Can one MLA see another MLA's complaints?
Technically impossible. PostgreSQL RLS enforces app_id isolation at the database engine level. Even if application code has a bug, the database refuses to return cross-tenant data before the query completes.
PostgreSQL RLS · app_id on every row · USING (app_id = current_setting(...))
BUILT AND LIVE ✓
❓What if an MLA loses an election?
All complaint data is retained permanently. The new MLA inherits the constituency portal with full history. The outgoing MLA's staff accounts are deactivated immediately. Complaint records belong to the constituency — not the individual MLA.
Soft-delete on staff accounts · constituency_id not linked to MLA person · audit log immutable
BUILT ✓
❓What if internet goes down in a village?
Citizens file complaints when connectivity returns — the link works on 2G and above. Staff dashboard caches complaint queue for offline viewing. SMS OTP fallback available for low-connectivity areas. No data is ever lost.
PWA service worker · React offline cache · SMS OTP fallback · 2G optimised bundle
BUILT ✓ (PWA partial — SMS fallback planned)
❓Can the system handle 175 MLAs + MPs simultaneously?
Yes. Netlify CDN serves the React app from global edge nodes — unlimited concurrent users. Supabase PostgreSQL auto-scales. No single server. Deno edge functions are stateless and scale independently. Designed for 50,000+ daily active users.
Netlify CDN · Supabase auto-scaling PostgreSQL · stateless Deno edge functions
ARCHITECTURE BUILT ✓ — load test planned before state rollout
❓Where is citizen data stored — India or abroad?
All data stored in Supabase India region (Mumbai — AWS ap-south-1). No data leaves Indian territory. Compliant with IT Act 2000 and data localisation requirements. No foreign government access possible.
Supabase ap-south-1 (Mumbai AWS) · India data residency · IT Act 2000 compliant
BUILT ✓
❓Can a citizen submit the same complaint multiple times?
Each citizen has one verified profile per phone number (OTP enforced). Duplicate submissions are flagged automatically. Staff can merge duplicates. Citizens see their own open complaints before filing — preventing re-submission.
Unique constraint on citizen_phone · duplicate check on submit · history visible to citizen
BUILT ✓
❓What if a staff member is dismissed — can they still access data?
Admin deactivates the account in one click. JWT tokens are blacklisted immediately — active sessions terminated within 60 seconds. All past actions remain in the audit log permanently. Deactivated accounts cannot log in again.
Supabase auth.users disabled · JWT max-age 1hr · audit log immutable · instant deactivation
BUILT ✓
❓How does the Minister see only their department's complaints?
The minister role is linked to one or more complaint categories (e.g. Water Resources Minister → category: water_supply). A PostgreSQL view filters complaints by category before returning to the minister's dashboard. Personal citizen data is masked in the view.
minister_categories table · filtered SQL view · PII masked at DB view · category-scoped RLS
PLANNED — 2 weeks development after pilot
❓How does the CM's office see all complaints without PII?
The state_admin role gets a separate read-only aggregate view — counts, categories, resolution rates, MLA rankings. Individual citizen names and phone numbers are never returned. Aggregation happens at the database view level, not the application.
state_admin role · aggregate-only SQL views · PII stripped at DB view level · read-only RLS policy
PLANNED — ready after Mandapeta pilot
❓Is the WhatsApp integration secure?
WhatsApp Business API via Twilio uses end-to-end encryption. MPower sends outbound template messages only — no citizen data stored at Twilio beyond phone number and approved message text. API keys stored in Supabase vault, never in source code.
Twilio WhatsApp Business API · E2E encryption · outbound only · secrets in Supabase vault
BUILT ✓
❓What happens to data if MPower shuts down?
Government receives full database export in standard PostgreSQL format monthly. All data exportable at any time by the state government. No proprietary formats. Government can migrate to any PostgreSQL-compatible system independently.
Monthly pg_dump · government-controlled S3 bucket · open PostgreSQL format · no vendor lock-in
PLANNED — data export agreement before state rollout
❓How is security audited and certified?
Supabase infrastructure is SOC 2 Type II certified. All security events are logged to an immutable audit table with SHA-256 hashes. MPower will undergo CERT-In empanelled VAPT before state rollout. Government IT team can audit independently.
SOC 2 Type II (Supabase) · SHA-256 audit trail · VAPT before rollout · open audit rights
SOC 2 inherited ✓ · VAPT planned before state rollout
